Findings 1–3, 5, 6, 9 · implemented

01

The catalogue shipped ~300 MB of base64 images

Fixed

Only the last-resort live-fetch branch wrote to static/img_cache. Every local-disk branch called image_path_to_data_uri(), which read the full-resolution original and base64-inlined it into the iframe srcdoc — for a 100 px image band. Two bugs compounded it: no downscaling (median source 51 KB, largest 1 MB), and a memo keyed on (url, eetra_id, name), so 552 distinct files were re-encoded once per each of the 1,580 rows referencing them.

What changed

All branches now route through static/img_cache: downscaled once to the existing theme.json → image_band.fetch_max_* budget (300×300), written as WebP with a per-thread temp file and os.replace, and referenced as a short URL. The memo keys on the image URL alone. No JavaScript changed — productImageSrc → appStaticUrl already resolved /app/… paths and the tags already carried loading="lazy".

02

The payload build ran on every rerun

Fixed

fn336_render_catalogue_flipcard rebuilt ~600 lines of payload on every Catalogue rerun — each search keystroke, tag toggle and document click. Profiling found four distinct causes, not one.

What changed

Badge composite: fn346_voc_cert_composite_data_uri was 7.9 s of the profile — 1,198 calls re-opening two PNGs, resizing and encoding, for just three reachable results. Memoized on the derived kinds tuple, so "M1", "M1 class" and "M1 classification" share one entry.

Tags: one groupby pass replaced fn407_get_tags_for_product per row, which was copying the whole tags frame and re-resolving its path 1,609 times.

Row extraction: the frame arrives as 125 string columns and 10 Float64, so pandas rebuilt the common dtype across all 135 on every row access — find_common_type alone was 8 s. One astype(object) (5 ms) removes the search entirely.

The cache: the build moved into _fn336_cached_catalogue_payload, keyed on the frame plus a config signature covering field visibility, display params and the tags mtime. Only theme/session CSS, cols, height, open_product and doc_preview stay live per rerun.

03

Filesystem probing on a OneDrive volume

FixedEstimate corrected

Three media resolvers shared one shape: build a candidate filename, is_file(), repeat across five or six extensions and up to two directories. static_img_cache_url alone was up to eight probes per call, called up to three times per image — and Finding 1 had made it the primary lookup, so this was partly self-inflicted.

What changed

_dir_file_index() lists a directory once into a dict and answers every candidate from it, with the freshness check itself rate-limited to 2 s — a first attempt that re-stat'd the directory per lookup only traded eight syscalls for one. Files this process writes register immediately, so the served store is never stale for its own writes. fn_sync_static_doc_links and _static_doc_file_info moved to os.scandir, whose directory enumeration already carries size and mtime.

06

Three parallel image caches

Fixed

01_data/img (pipeline originals, sha256[:16]), .cache/images (fetch cache, md5 with a __catalogue filename variant) and static/img_cache (served thumbnails, md5) held overlapping content under three key schemes. Every caller of fn110_cached_fetch_image passes profile="catalogue" — the legacy 300×160 profile had no callers left, so 238 of those files were from a retired code path.

What changed

fn110's fetch tier now reads and writes static/img_cache, the same store the catalogue serves from. That leaves two directories with clearly separate jobs: pipeline source of truth, and served thumbnails. 04_tools/10_consolidate_image_caches.py checks the legacy store for anything unique before removal — it found 7 candidates, all of which turned out to be 50×50 CDN error graphics that the app's own catalogue_image_cache_is_valid rejects. Nothing was lost; .cache/images was deleted.

05

Four byte-identical copies of the dataset

Fixed

base_data.parquet, live_data.parquet and copies of both under 01_data/ all hashed to 5f1736c1…. live_data.parquet was a materialised base ⊕ edits merge, rewritten after every save so that modules reading it directly — the document-path map, the tags layer, the manufacturers page and four offline tools — would not have to merge for themselves. A third copy of rows that already lived in two files, and a way for a failed write to serve stale data silently.

What changed

Two files remain, both in 01_data/ beside the rest of the project's data: base_data.parquet (the Excel conversion, written only by the pipeline) and edits_data.parquet (the append-only log of everything done through the app's form). The merge is no longer stored — fn159_effective_dataset() derives it on read, cached on both files' mtimes, and every former direct reader now calls it. The Excel pipeline stops emitting the duplicates. Path resolution prefers 01_data/ and falls back to the old root location, so an un-migrated checkout still starts.

requirements.txt was missing half its dependencies

Fixed

Ten of the twenty-three packages the code imports were declared. A clean deploy failed on the first chart. Rebuilt by walking every import across app.py, libs/, pages/, 04_tools/ and 05_tests/ and mapping each module to its distribution, rather than by memory.

What changed

Two things surfaced while checking. pyarrow was never declared even though every parquet read depends on it. Follow-on work

Two questions asked after the nine findings were closed. Neither was on the original list; both changed the code.

A

Can static/ fold into 01_data/?

Evaluated — no

Read out of Streamlit 1.60's own source rather than assumed. Three findings, any one of which settles it:

The name and location are hardcoded. file_util.get_app_static_dir() is literally Path(app.py).parent / "static". There is no config option pointing it elsewhere.

A symlink would work and would be a mistake. The route calls os.path.realpath() on the root, so static → 01_data would resolve and serve. It would also publish base_data.parquet, edits_data.parquet, tags.parquet and all 904 PDFs over HTTP with Access-Control-Allow-Origin: * — and these are server routes that never execute the script, so they bypass the login gate entirely.

It would break regardless. bootstrap.py walks the folder at startup and, above MAX_APP_STATIC_FOLDER_SIZE (1 GiB), calls config.set_option("server.enableStaticServing", False) — silently, for the whole process. 01_data is 1.3 GB, so the merge would disable static serving and take out both the document panel and every catalogue image.

Conclusion

The two directories have genuinely different jobs: 01_data is private source of truth, static/ is the public serving window, and only the second can be reached by a browser. The split stands. One incidental find: static/fonts/ronzino/ (180 KB) is referenced nowhere — theme.json's local_fonts is empty and nothing loads those faces.

Corrections to this audit

Two estimates in the original report were wrong, and two bugs were introduced during the work and caught before delivery. Recording them because the numbers above are only worth what the method behind them is.

Finding 3's cost was overstated by roughly 15×

The instrumented profile attributed 4.48 s to stat calls. Measuring actual syscall latency afterwards put it at 12–17 µs per call — the rest was my own measurement wrapper. The syscall count in the original report (≈11,000) was right; the cost attributed to it was not. Real saving: ~0.3 s on a cold render, ~0 on warm reruns.

Kept anyway on two grounds: os.scandir of the whole 562-file directory costs ~992 µs against ~194 ms of stats, so it still nets positive; and these figures are for locally-hydrated files. A OneDrive Files On-Demand file dehydrated to cloud-only blocks on network per stat, and 133 of those is survivable where 11,711 is not.

"read_iframe_component re-reads the template every render" — not a hot spot

Claimed in the original report as per-render overhead worth memoizing. Measured: three file reads, under a millisecond, absorbed by the OS page cache. Left alone rather than adding a memo for nothing.

Introduced: underscore-prefixed cache parameters key nothing

The first version of the payload cache named its parameters _is_js2 and _config_signature. Streamlit excludes underscore-prefixed parameters from the cache key, so neither keyed anything — a field-visibility edit would have silently served a stale catalogue. Caught by the invalidation test (0.057 s where a rebuild was due), renamed, and the trap recorded in the docstring. _progress keeps its underscore deliberately, being a live widget handle.

Introduced: a cached progress bar took the Catalogue down

The payload cache drove a progress bar belonging to a placeholder created by the calling page. @st.cache_data records the Streamlit element calls a cached function makes so it can replay them on a hit — and on a hit that placeholder no longer exists, so every cached render raised CacheReplayClosureError. It could only fail on a cache hit, which is exactly what the bare-mode test harness never exercises; it reached the user before it reached a test.

The bar is gone, replaced by the decorator's own spinner, and the regression is now covered by an AppTest run that drives one miss followed by two hits under a real script runner.

Introduced: a legacy PNG silently shadowed the rebuilt thumbnail

static_img_cache_url probes .png before .webp, so that entries written by older versions keep resolving. When the tier rebuild wrote a new 200 px WebP beside a leftover 300 px PNG of the same key, the probe kept returning the PNG and the rebuild appeared to do nothing for those images. Writes now prune same-key files at other extensions, so one key means one file; verified zero keys present at more than one extension.

Introduced: the cache migration shipped CDN placeholders

The first run of 10_consolidate_image_caches.py rescued 7 "unique" images into the served store. Inspection showed all were 50×50, 918-byte CDN error graphics — below the 64 px floor the app's own catalogue_image_cache_is_valid enforces. The migration had laundered rejected placeholders into a store the catalogue trusts on sight. The tool now applies that same admission test; the six files were removed and coverage returned to baseline.

Findings 4, 7, 8 · open and unresolved

04

OneDrive does not preserve hard links

Open

01_data/pdf is 1.3 GB and static/docs hard-links 702 MB of it — verified sharing inodes (nlink = 2), so locally it costs nothing. In the cloud, OneDrive uploads both as independent files: ~2 GB of tenant quota and sync bandwidth for 1.3 GB of PDFs.

Recommended

Exclude static/docs, 01_data/img, __pycache__, .pytest_cache and logs/ from sync. OneDrive has no .gitignore equivalent, so this means either moving the repo out of the synced tree or using per-folder exclusion.

07

Collections is missing from the nav bar

Could not reproduce

The original report repeated the diagnosis in app.py's comment — a Streamlit limit on flat position="top" pages — and proposed passing a dict to group them. Neither holds up.

A faithful reproduction (the same five page files, same titles, same icons, same order, an expanded sidebar, the admin sixth page, and st.navigation called late in the script) renders all six links, Collections included. The app's global CSS was dumped and searched: nothing hides a nav item. Five flat pages is nowhere near an overflow threshold.

Status

Left unchanged rather than applying a speculative fix. The real nav only exists past the login gate, so confirming it needs a signed-in session. If it still happens there, the cause is something the reproduction does not capture — and the grouped-dict change proposed earlier would likely not have addressed it.

08

No url_path on any page

Open

Every deep link and hard reload bounces to Welcome, which is why ?view_docs_for= needs a whole fallback path in app.py. Adding url_path= to each st.Page gives real URLs and lets that fallback be deleted.

Found in passing

Not part of the original nine; surfaced while measuring.

—

Cold start now waits on failing network fetches

Open

With disk and CPU addressed, the ~3.7 s cold render is dominated by http.client waiting on the 13 image URLs that no longer resolve. Those failures aren't negative-cached, so every process start re-attempts them against a 20 s timeout. This is now the largest remaining win on the catalogue path.

—

products_json is 11.2 MB, almost all rawFields

Product decision

Every one of the 135 columns, as strings, for every product, shipped on every view to serve the XL grid size. Images are now 0.13 MB of it. Trimming to the columns XL displays — or fetching on demand when someone switches to XL — is the next big cut, but it's a decision about that view rather than a mechanical optimisation.

—

One pipeline output is not an image

Pipeline

01_data/img/7ed83ddbe52fe2ab.aspx (25 KB) fails to decode — almost certainly an HTML error page saved with an image extension. That card's image was already broken in the browser; the new code degrades identically.

—

Authentication

Open

fn111_get_auth_users hard-codes a fallback admin credential in source, compares passwords in plaintext with ==, and the gate screen pre-fills that admin password. Fine for an internal tool on a trusted network; not fine if this is ever reachable beyond it.

How this was verified

  • Payload compared key-by-key after every stage — all six pre-existing keys byte-identical to baseline; the only delta is a newly-returned list_fields_json, which the Charts consumer reads via .get().
  • Cache invalidation exercised for a filter change, a FIELD_VISIBILITY edit (1.27 s rebuild) and a tag edit — the last by writing a real tag to BBW__GYP__0002, confirming it appeared, then restoring tags.parquet md5-identical.
  • Dynamic arguments and session CSS confirmed live on cache hits: toggling card borders and switching detail level to Extended both take effect in 0.11 s.
  • All 1,609 image URLs resolve identically through the directory index and direct is_file() probing; 200 document names likewise, present and missing.
  • fn_sync_static_doc_links makes byte-identical decisions to the old implementation (649 skipped, 255 budget-skipped), leaves static/docs unchanged, keeps all 649 hard links, and is idempotent.
  • Served over HTTP from the running app: /app/static/img_cache/ returns 200 image/webp, /app/static/docs/ returns 200 application/pdf, both with access-control-allow-origin: * — which is what lets the sandboxed srcdoc iframe (origin "null") load them.
  • ./static totals 708 MiB, under Streamlit's 1 GiB startup cap, which is checked once at boot and silently disables static serving app-wide if exceeded.
  • Dataset consolidation: all four parquets confirmed byte-identical before the move; the two survivors verified md5-identical after it; the catalogue payload byte-identical across the change.
  • The Add/Edit round-trip re-tested end to end — an update replays over base with no audit-column leakage and no row-count change, a new id appends (1,609 → 1,610), and edits_data.parquet was restored byte-for-byte afterwards.
  • Every former live_data.parquet reader re-checked: the document-path map still returns 1,609 ids, manufacturer counts still cover 84 manufacturers, the tags layer still resolves 01_data/.
  • Dependency floors checked against the installed environment: 22 of 23 satisfied, the exception being portalocker, which is genuinely absent.
  • Image tiers verified in the live component against real data: the card slot loads <md5>.webp at 200×150, the panel loads <md5>__d.webp at 400×300 into a 98×74 box, both served 200 with an ETag so any cached 300 px copy revalidates away.
  • 8/8 existing tests pass; everything compiles; app boots with no server errors.
